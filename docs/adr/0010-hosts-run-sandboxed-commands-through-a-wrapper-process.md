# Hosts run sandboxed commands through a wrapper process

A sandbox's proxies have to live exactly as long as the command they serve. kelpie's `Sandbox` port hands back a `std::process::Command` for the caller to spawn, and today that command is `node` running upstream's CLI, so each call gets its own proxies, gone when its command exits. crabpot keeps that shape. The library's core is a `Sandbox` value that starts the proxies from a config, wraps a `&Command` into a new `Command`, and stops the proxies when it drops. On top of it, `run_from_args()` lets a host's own binary act as the wrapper: the host calls it first thing in `main`, and when the arguments start with `--crabpot` it parses the CLI's own arguments, runs the command inside its sandbox, and exits with it. The `crabpot` CLI is the same code. The parser is hand-written in the library, so a host built without the `cli` feature (ADR-0009) still has it.

Off Linux, the child stays in the wrapper's process group. On Unix, the wrapper and Linux helper forward SIGINT, SIGTERM, SIGHUP, SIGQUIT, SIGUSR1 and SIGUSR2. Forwarding more than upstream's SIGINT and SIGTERM is a deliberate difference: a supervisor can choose another shutdown signal, and the wrapper must keep the sandbox and its proxies alive while the command drains. The wrapper's exit status is mapped as upstream maps it: only SIGINT and SIGTERM are a clean stop. A host that signals the wrapper's group, as kelpie does, reaches the command, directly or through the wrapper's forwarding, and the wrapper together. Ending a command's whole process tree from inside crabpot is left for after kelpie-ready, built on a process-tree crate shared with shep and kelpie rather than a third copy of that code.

On Linux, the wrapper targets the helper below bwrap's monitor and namespace init, following their child PIDs in the host's `/proc`: the `children` file where the kernel has one, and each process's parent pid in `stat` where it has not (a kernel built without `CONFIG_PROC_CHILDREN`, gVisor). Bwrap's monitor does not forward signals. Signalling it directly kills the monitor and, through `--die-with-parent`, the sandbox. The monitor stays alive to report the helper's exit status.

Two things keep a signal from reaching bwrap's processes. The wrapper starts bwrap in a process group of its own, so a host that signals the wrapper's group reaches the wrapper, which forwards, and not bwrap as well. And bwrap starts with the forwarded signals blocked, a mask every process down to the helper inherits, so a signal that arrives before the helper has handlers stays pending. The wrapper retries discovery every 10 ms, and the helper forwards the signal once it has handlers. The command gets the mask back before it runs. Waiting ends when the signal is forwarded or bwrap exits and the forwarding tasks are aborted.

## Considered options

- **The `Sandbox` value alone.** Rejected because a port that returns a `Command` has nowhere to keep the value alive, so every caller in kelpie would have to change.
- **Depend on shep's supervision code for cleanup.** Rejected because `shep-daemon` is a whole async engine, and the parts that end a process tree are private to it.
- **`run_from_args` behind the `cli` feature.** Rejected because kelpie builds without it, and five flags do not need a parser crate.
